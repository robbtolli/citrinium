# Milestone 6 — Full Live Preview Editor

Parent: [`milestones.md`](../../milestones.md)

## Objective

Deliver the `design.md` §7 editor: an Obsidian-style Live Preview surface where **the edit buffer is always the literal file content**, markup is rendered/collapsed based on cursor position, and every Markdown affordance an author needs (checkbox toggling, link following, list continuation, emphasis shortcuts, `[[`/`#`/`@` autocomplete) works without ever introducing a document-tree round trip.

M1 ships the *first slice* of this same editor, not a disposable prototype: a custom `TextEditingController` + decoration overlay over `MarkdownDocument.rawText`, deliberately restricted to task-checkbox rendering/tap-to-cycle-state, BuJo event/note signifier glyphs, and basic bold/italic hide-near-cursor (see `m1.md`'s "Editor scope" decision). M6 completes the decoration set M1's reduced scope deliberately left out — cursor-aware wikilink bracket-hiding, embed rendering, block-ID visual treatment, heading/emphasis polish beyond bold/italic — and adds the surrounding engineering a single-milestone reduced-scope pass couldn't responsibly include: viewport-scoped incremental decoration/caching, the full editing-affordance set, `[[`/`#`/`@` autocomplete, and the save/external-change-reconciliation pipeline. See "Shared foundations with M1" below — the architecture in this document is not M6-exclusive.

## Why it's a milestone and not a UI task

`design.md` §7 says this is "a genuine engineering investment (Flutter provides no CodeMirror-equivalent decoration engine out of the box)." Concretely, Flutter gives us exactly one supported extension point for styled editing — `TextEditingController.buildTextSpan` — and it is a *pure restyle* hook: it cannot hide characters, cannot reorder them, and is re-invoked on every keystroke and every caret move over the whole document. Everything else in this milestone is engineered around those three constraints.

## Exit criteria

1. **Offset identity, proven mechanically.** For every fixture in the M0 corpus, the concatenated plain text of the span tree returned by `buildTextSpan` is **byte-identical** to `controller.text`, in every reveal state. This is the invariant that makes selection, caret movement, IME, and undo correct by construction rather than by inspection.
2. No decoration path can mutate the buffer. Rendering is a pure function `(rawText, blockContext, revealSet) → List<Decoration>`; the only writers are explicit user intents.
3. Round-trip integrity is preserved end-to-end: open a fixture in the editor, tap a checkbox, save, and only the expected byte range on disk changed (extends M0 exit criterion 3 through the UI).
4. Typing sustains 60fps on a 2,000-line / ~150 KB note on the Linux reference machine and a mid-tier Android device, with decoration computation viewport-scoped (W2/W3) so that cost tracks visible lines rather than document size; caret movement across lines does not drop frames. Above a configured size threshold — driven by the native paragraph-layout cost that viewport scoping does **not** remove — the editor degrades **visibly and deliberately** to undecorated source with a banner, never silently to jank.
5. Incremental decoration is provably equivalent to full re-decoration under randomized edit sequences (property test).
6. Golden tests cover every decoration kind × {collapsed, revealed} × {light, dark}.
7. External modification of the open file while the buffer is dirty never loses either side silently — the user is offered an explicit choice.
8. Manual platform pass: soft keyboard + autocorrect on iOS/Android, CJK IME composition, desktop mouse hover/selection/modifier-click, and text-scale factor 2.0.

## Decisions locked for M6

| Area | Decision |
| --- | --- |
| Base widget | **`EditableText`, not `TextField`.** See "Clarification to design.md §7" below. `TextField` hides `editableTextKey`, its `TextSelectionGestureDetectorBuilder`, and `renderEditable` — all three are required (hit-testing decorations, anchoring autocomplete at the caret rect). `EditableText` *is* the `TextField` family; we reimplement only the Material chrome we actually want. |
| Hiding mechanism | **Metrics collapse, never text substitution.** Markup characters stay in the span tree and are styled to ~zero advance. Buffer-rewriting "fold" schemes (what `flutter_code_editor` does) are ruled out: they make the controller's text a *view* of the file rather than the file, which directly contradicts `design.md` §7. |
| Glyph substitution | Only via a **1-character `WidgetSpan`**. A `PlaceholderSpan` occupies exactly one code unit (U+FFFC) in `TextPainter`'s offset accounting, so 1 char → 1 widget is offset-exact; 5 chars → 1 widget is not. `- [x]` therefore decomposes to: collapse `- [`, replace the single marker char with a `WidgetSpan`, collapse `]` + following space. |
| Block-level geometry | A **`CustomPaint` backdrop behind the editable layer** (code-block fills, blockquote bars, indent guides, active-line tint, hrules). Anything that isn't expressible as a per-character `TextStyle` goes here, where it cannot touch offsets. |
| Reveal granularity | **Node-level for inline syntax, line-level for block markers.** A node reveals iff the selection range touches `[node.start, node.end]` inclusive. Predictable and matches Obsidian's feel; see "Reveal policy". |
| Decoration engine location | **Pure Dart in `packages/citrinium_core`**, emitting *semantic* decorations (offsets + kind + role). The Flutter layer owns kind → `TextStyle`/widget mapping. Keeps ~80% of the logic in fast unit tests and out of goldens. |
| Decoration scope | **Viewport-scoped, not whole-document, from v1** — not a later optimization. Only lines within the viewport + a margin run through the W1 semantic scan and the `WidgetSpan` glyph-substitution mapping; off-screen lines render as plain, undecorated source until they scroll into range. Bounds the *decoration-computation* cost to O(visible lines). It does **not** bound the native `TextPainter`/paragraph-layout cost, which stays O(document) on every reveal-triggered edit regardless — that residual ceiling is why exit criterion 4's size threshold still exists (see Risks). |
| Offset units | Dart `String` **code units**, inherited unchanged from M0. Non-negotiable: `📅⏰🔁` are surrogate pairs, and a collapse run boundary that splits one corrupts rendering. |
| Whole-line collapse | **Forbidden in v1.** A line whose every run is collapsed has near-zero height and the caret becomes unhittable. Frontmatter delimiters and fence lines are *dimmed*, not collapsed. |
| Checkbox tap semantics | Tap cycles `open → completed → open`; long-press/right-click opens the full D-02 state menu. The mutation is a **1-char buffer splice through the controller**, so it lands in the normal undo stack and the normal debounced save — not a round trip through the file watcher. |
| Link tap semantics | Tap **follows** a link only while it is collapsed (rendered); once revealed (caret on the node) tap places the caret. Derived from the reveal model, so it needs no separate mode. Ctrl/Cmd-click always follows. |
| Source mode | A per-view **Live Preview ⇄ Source** toggle. Cheap (it's `revealSet = all`), and the primary debugging tool for the whole milestone. |
| Transclusion | `![[embed]]` renders as a link chip in v1. Real inline transclusion is post-1.0 (needs nested layout, and belongs with M9's link graph). |
| Tables / images | Not rendered in v1 (tables need a real grid, images need `N-06`, a COULD). Styled as monospace/dimmed source. Recorded as a known gap, not an oversight. |

### Clarification to design.md §7

§7 says "built on Flutter's `TextField`/`TextEditingController`". M6 builds on **`EditableText`** — the widget `TextField` itself wraps — plus a `TextEditingController` subclass. This is a refinement of the same decision (plain-text buffer + decoration layer, no document tree), not a reversal, but per `AGENTS.md` it is stated explicitly rather than done silently. `design.md` §7 should be amended to say "`EditableText`/`TextEditingController`" when this milestone is accepted.

**Fallback if `EditableText` proves too raw** (W0 decides): keep `TextField`, accept that only `WidgetSpan` children are hit-testable (checkboxes and bullets keep working, since their children are real widgets with their own `GestureDetector`), lose tap-to-follow on collapsed links, and anchor autocomplete with a shadow `TextPainter` that mirrors the field's layout.

### Shared foundations with M1

`m1.md`'s W5 ("Reduced-scope Live Preview editor") builds task-checkbox rendering, BuJo signifier glyphs, and basic bold/italic hide-near-cursor — a strict subset of this document's decoration set (`DecorationKind` in W1 below already lists `taskMarker`, `eventBullet`, `noteBullet`, `strong`, `emphasis` alongside the M6-exclusive kinds like `wikilink`/`embed`/`heading`/`blockId`). **This is one editor built in two increments, not two editors.** Every row in "Decisions locked for M6" above — base widget, hiding mechanism, offset-identity invariant, viewport-scoped decoration — governs M1's W5 just as much as it governs this milestone, because M1's decoration overlay and M6's are the same `TextEditingController` subclass and the same underlying engine, extended.

Two sequencing consequences, since M1 is scheduled first but this document is the one that works out the architecture in depth:

- **If M1's W5 is implemented before this document is consulted**, there's a real risk of it independently reinventing (and potentially getting wrong, or getting right but incompatibly with) the offset-identity/hiding-mechanism/base-widget decisions above. `m1.md` should be treated as needing a cross-reference to this document's W0 spike findings and "Decisions locked" table before W5 starts, not as an independently-resolved milestone.
- **If M1's W5 ships first**, M6's W1 (semantic decoration engine) and W3 (live preview controller) are "extend the existing engine with new `DecorationKind`s and reveal rules" rather than "build from scratch" — the workstream breakdown below is written at full-build depth because, as of this document's last revision, M1's W5 has not yet been implemented (no editor code exists in the tree); reconcile scope against whatever M1 actually ships before starting M6's W1.

## Dependencies to add

Deliberately close to zero — this is our own engine, and pulling in a Markdown package would reintroduce the parse↔serialize round trip §7 exists to avoid.

- **`packages/citrinium_core`**: none. Reuses `characters`, `collection`, `meta`, `freezed` from M0.
- **Root app**: `super_clipboard` or platform channels **only if** rich paste (HTML → Markdown) is pulled in from stretch scope; otherwise nothing. Dev: `flutter_test` goldens (already present).
- Explicitly **not** added: `flutter_markdown` (renderer, not editor — wrong shape and now discontinued), `flutter_quill`/`super_editor`/`appflowy_editor` (document-tree editors, rejected in `design.md` §7), `flutter_code_editor` (buffer-rewriting folds, rejected above).

## Workstreams

### W0 — Spike: prove the rendering primitives (~3–5 days, gates everything)

Nothing downstream is safe to schedule until these four questions have measured answers. Timebox hard; each has a named fallback.

1. **Zero-advance collapse.** Can a `TextStyle` run be made visually absent while still occupying its characters? Candidates, in order: `fontSize` near-zero (`0.01`) + `transparent` color; negative `letterSpacing` cancelling advance; `height` left unset so a tiny run never shrinks the line box (line height is the max over runs — verify). Measure with `TextPainter`: the x-advance of a collapsed run must be < 0.5 logical px, and the line's height must be unchanged versus a line without the run.
   *Fallback: dim markup to ~25% opacity instead of hiding it.* Less Obsidian-like, fully shippable, zero risk. **Decide this in W0, not in W3.**
2. **`WidgetSpan` inside an editable.** Does a 1-char `WidgetSpan` in `EditableText` keep caret offsets exact, paint selection highlight sanely across itself, and hit-test its child on all five platforms? Also check `PlaceholderAlignment` baseline behaviour against surrounding text.
   *Fallback: no glyph substitution — checkboxes render as styled source (`- [x]` with the marker char emphasised) and toggling moves to a gutter affordance painted in the backdrop layer.*
3. **Rebuild cost.** Confirm `buildTextSpan` is re-invoked on selection-only changes (it must be, for cursor-aware reveal to work at all — `EditableText` rebuilds when the controller notifies, and setting `value` for a caret move notifies). Then measure: full-document span rebuild + `TextPainter` relayout at 500 / 2,000 / 10,000 lines. This produces the concrete size threshold for exit criterion 4.
4. **Emoji metadata across platforms.** Measure and render `📅 2026-08-01 ⏰17:00 🔁 every weekday` on all five platforms. Flutter's emoji fallback is platform-specific; confirm collapse math on surrogate pairs and that no platform renders tofu. If any does, the FR-04 schema needs an ASCII-alias escape hatch — which is a **`docs/file-schema.md` change**, so it must be found now and not in M12.

Deliverable: a throwaway `example/` app plus a written verdict on each of the four, appended to this document.

### W1 — Semantic decoration engine, pure Dart (~5–7 days)

`packages/citrinium_core/lib/src/markdown/decoration/`. The core deliverable of the milestone.

```dart
enum DecorationKind {
  // inline emphasis
  strong, emphasis, strikethrough, highlight, inlineCode,
  // structure
  heading, listMarker, bulletGlyph, taskMarker, blockquoteMarker,
  fenceDelimiter, frontmatterDelimiter, thematicBreak,
  // links
  wikilink, wikilinkAlias, embed, inlineLink, autolink,
  // Citrinium inline metadata (design.md §3.2)
  dueDate, dueTime, recurrence, context, tag, blockId, signifier,
  // BuJo bullets (design.md §3.2)
  eventBullet, noteBullet,
}

/// Which part of a syntax node a span covers -- this is what decides
/// collapse vs. style, so it is modelled explicitly rather than inferred.
enum DecorationRole { openMarker, closeMarker, content, whole }

class Decoration {
  final int start;          // code-unit offsets into rawText
  final int end;
  final DecorationKind kind;
  final DecorationRole role;
  final int nodeId;         // groups markers with their content for reveal
  final int? level;         // heading level, list depth
  final String? payload;    // link target, tag name, parsed date...
}
```

- **Block context lexer.** Per-line resumable state (`inFence(fenceChar, fenceLen, infoString)`, `inFrontmatter`, `quoteDepth`, `listStack`) so a fence opened on line 40 correctly suppresses inline parsing to line 90. Modelled as a lexer state machine with comparable states, which is precisely what makes W2's incremental invalidation terminate early.
- **Inline scanner** over non-code regions: emphasis with correct left/right flanking-delimiter rules (`snake_case_word` must **not** italicise — this is the single most common naive-implementation bug), backtick runs, wikilink/embed/inline-link forms, and the §3.2 inline metadata grammar.
- **Precedence is explicit**, not incidental: inline code beats everything inside it; a fence beats a heading; frontmatter (offset 0 only, per M0) beats all; escapes (`\*`) suppress.
- **Reuses M0's parser output where it exists** (`ParsedLine`, task markers, inline-metadata spans, wikilink spans) rather than re-lexing. Where the decorator would need to duplicate M0 logic, extract it into a shared scanner and make M0 use it too. A **parity test** asserts the decorator and the parser agree on every span they both claim — a divergence here is an FR-04 conformance bug in one of them.

### W2 — Incremental, viewport-scoped decoration + caching (~4–5 days)

Full re-decoration per keystroke misses exit criterion 4 by an order of magnitude on large notes — and decorating the whole document regardless of what's actually on screen wastes work even below that threshold. Viewport scoping is part of the v1 design here, not a fast-follow.

- Line index with dirty tracking; an edit at `[start, end)` invalidates only the lines it spans.
- **Forward block-context propagation with early termination**: recompute lines forward until the entering block context equals the previously cached one, then stop. Typing inside a paragraph touches 1 line; typing a ``` fence propagates until it converges.
- **Viewport + margin gating**: a scroll listener maintains the current visible line range plus a margin of N lines above/below. Lines outside that range short-circuit *before* the per-line cache lookup — no decoration engine invocation at all, not even a cache-hit path. They render as plain, undecorated `TextSpan`s and carry no `WidgetSpan` checkboxes until they scroll into range.
- **A third invalidation trigger, alongside "text changed" and "selection changed": "visible range changed."** Pure scrolling with no text or selection change must still trigger decoration of newly-visible lines (computed lazily, on first visibility) and may drop cached decoration for lines that scroll back out of range under memory pressure. This is new relative to a purely reactive `buildTextSpan` model and needs its own listener wiring in W3's controller.
- Two-level cache: per-line `List<Decoration>` keyed on `(lineText, enteringBlockContext)`, and the built `TextSpan` tree keyed on `(documentVersion, revealKey)` — where `revealKey` is a hash of the revealed node-id set. **This is what makes caret movement cheap**: moving the caret within one node changes neither key, so the span tree is returned unbuilt.
- Randomized-edit equivalence test lives here, not in W10 — it's the acceptance test for the optimization. Extended to assert viewport gating never changes *what* a line eventually renders once scrolled into view, only *when* the work happens.

### W3 — Live preview controller + reveal policy (~4–5 days)

`lib/shared/markdown_editor/live_preview_controller.dart` — the `TextEditingController` subclass. Overrides `buildTextSpan` only; holds no authoritative state.

**Reveal policy** (`RevealPolicy`), specified because "cursor-aware" is otherwise unfalsifiable:

| Situation | Behaviour |
| --- | --- |
| Caret inside or touching an inline node | That node's markers reveal (`selection.start <= node.end && selection.end >= node.start`) |
| Non-collapsed selection | Every node it intersects reveals |
| Block markers (heading `#`s, list marker, `>`, fence delimiter) | Reveal iff the selection intersects **that line** |
| Frontmatter block | Dimmed always; revealed (full style) iff the selection intersects the block |
| Source mode on | Everything revealed, no `WidgetSpan` substitution |
| IME composing region active | **All decoration suppressed within the composing range** — non-negotiable, or the IME fights the decoration on CJK input. `withComposing` still renders the standard composing underline. |

Then `decoration_theme.dart` maps `(kind, role, revealed)` → `TextStyle` or `WidgetSpan`, honoring the M0 Material 3 calm theme, `MediaQuery.textScaler`, and light/dark. Marker colors are theme-derived at reduced emphasis, never hardcoded — T-05's contrast requirement applies to *revealed markup*, which is easy to make illegible.

Checkbox `WidgetSpan` substitution follows the same viewport gating as decoration generally (W2): a checkbox marker outside the visible range renders as plain source text (`- [x]`) rather than a widget, and is upgraded to its `WidgetSpan` form lazily the first time it scrolls into range. Without this, constructing widgets for thousands of off-screen checkboxes would dominate the per-scroll rebuild cost even after decoration itself is otherwise viewport-scoped.

Editor configuration that specifically matters for Markdown: `maxLines: null`, soft wrap, no horizontal scroll, and **`smartDashesType`/`smartQuotesType` disabled** — iOS's smart substitution silently rewrites `--` to an em dash and straight quotes to curly ones, corrupting code spans and link syntax in a file the user believes is plain text. `enableSuggestions`/autocorrect stay **on**; this is a notes app.

### W4 — Backdrop paint layer (~3–4 days)

A `CustomPaint` sized and scroll-synced with the editable, reading line-box geometry from `renderEditable`:

- Fenced/indented code-block background fills spanning the full content width.
- Blockquote and callout left bars, nested by depth.
- List indentation guides.
- Active-line tint (subtle; P-07 calm defaults — it must not read as a highlight).
- `---` thematic breaks drawn as a rule behind the dimmed source line.

Painted **behind** the text, so it can never perturb text metrics. Repaints on scroll/relayout only, via `RepaintBoundary`.

### W5 — Gestures, hit-testing & navigation (~3–4 days)

- Subclass `TextSelectionGestureDetectorBuilder`; override `onSingleTapUp`/`onSecondaryTap` to consult a decoration hit-test **before** falling through to default caret placement. Hit test = `renderEditable.getPositionForPoint(globalPos)` → offset → interval lookup over the sorted decoration list.
- Checkbox toggle (W0-dependent: `WidgetSpan` child `GestureDetector`, or field-level hit test).
- Wikilink follow → M0's document list / M9's resolver; unresolved targets render distinctly (Obsidian's dimmed-link convention) and offer "create note".
- Desktop `MouseRegion` hover: `SystemMouseCursors.click` over collapsed links, link-target tooltip.
- Long-press / right-click on a task marker → D-02 state menu (open / in-progress / completed / migrated / scheduled / dropped / waiting-for), which is also B-05's one-gesture bullet actions delivered inside the editor.

### W6 — Editing affordances (~4–5 days)

All implemented as `Actions`/`Intent`s over the controller so they participate in `EditableText`'s `UndoHistory` uniformly, and all are single buffer splices.

- **Enter**: continue the current list marker (preserving indent, task marker, and blockquote prefix); on an *empty* list item, remove the marker instead of nesting deeper.
- **Tab / Shift-Tab**: indent/outdent the list item (or the selected block of items) — not literal tab insertion when on a list line.
- **Cmd/Ctrl-B / -I / -K**: toggle `**`/`*`/link around the selection; with a collapsed caret, insert the delimiter pair and place the caret between them. Toggle must be *idempotent* — applying bold twice returns the original bytes exactly.
- **Smart paste**: URL over a non-empty selection → `[selection](url)`; multi-line paste onto a list line → prefix each line with the marker.
- **Cmd/Ctrl-Enter** on a task line: toggle completion.
- Shortcut activators built per-platform (`meta` on Apple, `control` elsewhere) with a single table, satisfying A-08.

### W7 — Caret-anchored autocomplete (~3–4 days)

`OverlayPortal` + `CompositedTransformFollower` anchored on `renderEditable.getLocalRectForCaret`, with flip-up-when-clipped and keyboard-safe-area handling on mobile.

- `[[` → note titles/aliases, from the M0 `documents` table.
- `#` → tags, from `entry_tags`. `@` → contexts, from `entry_contexts`.
- Queried through drift with a debounce and a result cap; arrow-key/Enter/Escape driven; **never** auto-accepts on blur (X-05: no silent edits).
- This overlay + query machinery is deliberately the same code M9's quick switcher (N-04) will reuse — build it factored for that.

### W8 — Save pipeline & external-change reconciliation (~2–3 days)

M1 has a debounced write; M6 is the first point where a *long-lived dirty buffer* exists, which makes the conflict case real.

- Write-through on idle (~800ms), on blur, on navigation, and on app lifecycle pause. Atomic write via M0's `vault_file_io`; the watcher's existing self-write suppression covers the echo.
- **External change while open:** if the buffer is clean, reload silently and preserve caret line. If dirty, show a **non-blocking banner** with "Keep mine" / "Load from disk" / "View difference" and write nothing until the user chooses. Nothing is auto-merged and nothing is discarded — the closest thing to T-03 semantics that exists pre-sync.
- File deleted externally while open → keep the buffer, offer "Save as new file".

### W9 — Integration into existing surfaces (~2–3 days)

Replace every M0–M5 text surface with the editor: M0's read-only raw file view, M1's rapid-log line editor and note body (D-14), M2's project files, M4's Monthly/Future Log and Collections, M5's migration/review notes. Two configurations of one widget — `singleLineish` (rapid-log capture: no backdrop, no block decoration, Enter commits) and `full` (document editing) — not two implementations.

### W10 — Tests, goldens & perf harness (~4–5 days, interleaved)

- **Pure-Dart unit tests** over the W1 engine — the bulk of coverage, and fast: emphasis flanking rules, fence suppression, escapes, precedence, metadata grammar, block-context propagation.
- **Offset-identity property test** (exit criterion 1) over the M0 hostile fixture corpus × every reveal state. Mechanically guarantees the whole hiding scheme.
- **Incremental ≡ full** randomized-edit equivalence (from W2).
- **Golden tests** per kind × reveal state × theme. Kept narrow and numerous rather than whole-screen, so a theme tweak doesn't invalidate 200 images.
- **Widget/integration tests**: tap a collapsed link follows / tap a revealed link places caret; Enter continues then terminates a list; checkbox toggle is a single undo step and a single-byte disk change; autocomplete keyboard flow; dirty-buffer external-change banner.
- **Perf harness** as a benchmark test with asserted budgets at 500/2,000/10,000 lines: span build, `TextPainter` layout, keystroke-to-frame.
- **Manual matrix** (not automatable, so scripted as a checklist): iOS/Android soft keyboard + autocorrect, CJK IME composition, desktop selection/hover/modifier-click, `textScaleFactor` 2.0, RTL paragraph.

**Rough total: ~37–50 working days.** W0 gates everything; W1→W2→W3 are sequential; W4–W7 parallelize across two people; W10 interleaves throughout.

### Cut lines, if the milestone must ship short

Ship: W0, W1, W2, W3, W5 (checkbox + link follow), W6 (Enter/Tab/emphasis), W8, W9, W10.
Cut first, in order: W7 autocomplete (→ M9, where it merges with N-04's quick switcher); W4 backdrop beyond code-block fills; smart paste; callout bars. None of these are load-bearing for another milestone.

## Risks

| Risk | Mitigation |
| --- | --- |
| Zero-advance collapse is unachievable or janky in Flutter's text engine | W0 spike gates the milestone; fallback is dimming markup, which is shippable and changes only the theme mapping in W3 |
| `WidgetSpan` in `EditableText` breaks selection painting or caret offsets on some platform | W0 tests all five; fallback is no glyph substitution + a gutter affordance |
| Full-document *native paragraph layout* has no line virtualization in `EditableText`, so that specific cost stays O(document) regardless of viewport — even though viewport-scoped decoration (W2/W3) already bounds the separate *decoration-computation* cost to visible lines | Hard size threshold with visible degradation (exit criterion 4) is the remaining mitigation for the layout-cost ceiling specifically, since viewport scoping doesn't touch it; genuinely huge single files are a vault-shape problem we decline to solve by other means in v1. **This is not hypothetical**: [flutter/flutter#114158](https://github.com/flutter/flutter/issues/114158) (closed **not_planned** — Flutter's own maintainers treat this as accepted architecture, not a bug) reproduces exactly our shape of problem — a custom decorating `TextEditingController` going slow on documents of "thousands of lines" — and separately shows plain `TextField` alone struggling on a ~7,600-line paste. [flutter/flutter#174688](https://github.com/flutter/flutter/issues/174688) independently reports lag starting around ~20,000 words (~120–150KB). These reports bracket the same low-thousands-of-lines zone the W10 perf harness already benchmarks (500/2,000/10,000 lines), which is corroborating evidence the plan is measuring the right range, not a false sense of safety from round numbers. See "Alternatives considered and not pursued" below for the windowing and `re_editor` foundations evaluated as ways to remove this ceiling entirely, and rejected for v1. Post-1.0, see "Post-1.0 large-file mode fallback" below for a UX-level (not architectural) mitigation layered on top of this same threshold. |
| Vertical caret movement into a collapsed line reflows on arrival, so the caret can land at a surprising column | Known quirk, documented; Obsidian has the same class of behaviour. No clean fix without offset remapping, which is ruled out |
| Emphasis flanking rules implemented naively italicise `snake_case` identifiers | Dedicated fixture set in W1; treated as a correctness bug class, not cosmetic |
| Decorator and M0 parser drift apart on the FR-04 grammar | Shared scanner + parity test in W1; a divergence is an FR-04 conformance bug, not a UI bug |
| IME composition fights decoration on CJK input | Decoration suppressed inside the composing range (W3), verified manually in W10 |
| Bidi/RTL text combined with collapsed runs produces caret anomalies | Acknowledged limitation for v1; recorded here rather than discovered in M12's A-08 pass |
| Building on `EditableText` means owning behaviour `TextField` gives free (Material chrome, magnifier, context menu, toolbar) | Reuse `AdaptiveTextSelectionToolbar` and `TextMagnifier` explicitly; budgeted in W3, and the W0 fallback is returning to `TextField` with reduced gesture scope |

## Alternatives considered and not pursued

Two related ideas were evaluated against `design.md` §7's remaining ceiling — full-document *native paragraph layout* on every reveal-triggered edit, since `EditableText` has no line virtualization — and are recorded here so neither is silently re-litigated nor silently forgotten. **Viewport-scoped decoration is not one of these**: that partial mitigation survived evaluation and is already part of the v1 design (see the "Decoration scope" row in Decisions locked, and W2/W3) — it is not deferred, and this section is about the two ideas that were rejected.

### Windowing `EditableText`'s buffer itself (rejected)

**The tempting idea:** feed `EditableText`'s controller only the text visible in the viewport (plus a margin), the way CodeMirror 6 (Obsidian's actual editor) only builds DOM/measures lines near the viewport — i.e. windowing the *text*, not just the *decoration*.

**Why it's rejected, worked through:**

- A `TextSelection` is just an offset pair into whatever string is currently loaded. Select across a window boundary (start in the loaded window, end past it) and there's nothing to represent the untouched half.
- An accurate scrollbar over an un-laid-out 5,000-line document needs its own per-line height model, since heights aren't uniform (headings, wrapped lines, code blocks) — a real chunk of what CM6 tracks internally, built as a bolt-on rather than something purpose-built for it.
- `EditableText`'s `UndoHistory` is scoped to the controller's value. Swapping the controller's content on every window slide risks an undo stack that stops meaning what the user thinks it means.
- P-11 requires the buffer to be the literal file; a window is only ever *part* of the file, so the untouched prefix/suffix must be tracked out-of-band and stitched back together correctly on every save, jump-to-line, and search hit — in effect a rope/piece-table, maintained by us, on top of a widget that assumes one flat string.
- No prior art was found of exactly this pattern (windowed substring fed into `EditableText`) — see the `re_editor` write-up below for what real large-text solutions do instead.

### `re_editor` as the rendering foundation (rejected for now; revisit trigger below)

[`re_editor`](https://pub.dev/packages/re_editor) (MIT, ~130 commits, actively maintained — v0.10.0 shipped within the last month as of this writing) is a from-scratch Flutter code editor — not built on `TextField`/`EditableText` at all — with real production mileage (it's Reqable's own shipping editor, plus used in several sizable open-source Flutter apps). It was evaluated as a possible rendering foundation for this milestone instead of `EditableText`, because it already has the one property `EditableText` structurally lacks: genuine per-line virtualized rendering (`_CodeParagraphProvider` builds one `ui.Paragraph` per line, only for lines currently in the viewport) — which would remove the native-layout ceiling entirely, rather than only bound the decoration-computation cost the way viewport-scoped decoration does.

**Why it isn't a drop-in fit, from reading its source directly (not just its README):**

- Its "content collapsing" feature is code folding — manually-triggered, whole-region hide/show — not proximity-based inline markup hiding. Used unmodified it renders Markdown-with-syntax-coloring, not an Obsidian-style Live Preview: a materially different reading experience from what this milestone specifies.
- Its paragraph cache (`_CodeParagraphProvider._cachedParagraphs`) is keyed on `TextSpan` *value equality*, which is structurally compatible with reveal-based caching — encouraging. But its highlighting-refresh path (`_CodeHighlighter._onCodesChanged`) explicitly no-ops when the underlying text is unchanged, i.e. it's architected to recompute on text changes only, never on selection-only changes. Whether its render layer's layout path independently re-invokes per-line paragraph building on a pure caret move (in which case a reveal-aware wrapper would largely just work) or would need new invalidation wiring (real, but bounded, surgery) was not fully resolved without deeper reading of its ~57KB render-object layout code — this single question is the actual fork/no-fork decision point, left unresolved since this path isn't being pursued now.
- `WidgetSpan` support (our checkbox-glyph mechanism) is very likely absent: `_ParagraphImpl.draw()` is a bare `canvas.drawParagraph(...)`, with no machinery reading placeholder rects back out to position/hit-test child widgets the way Flutter's own `RenderParagraph` does. A fork would need to port that — or, a good idea regardless of foundation, switch the checkbox glyph to an icon-font character swap via `TextStyle.fontFamily` instead of a widget.
- A real, currently open, exactly-relevant bug was found by reading the source: `_CodeParagraphProvider.trucate()` (used for its `maxLengthSingleLineRendering` option) does a raw `text.substring(0, n)` cut with no surrogate-pair awareness, matching open issue [reqable/re-editor#104](https://github.com/reqable/re-editor/issues/104) — precisely our 📅⏰🔁 metadata's risk zone. Its caret-offset math elsewhere *does* correctly handle surrogate pairs/ZWJ/bidi marks, so this isn't a uniformly immature codebase, just an inconsistently-covered one.
- Open performance issues in exactly its advertised strength ([reqable/re-editor#101](https://github.com/reqable/re-editor/issues/101): large-file scroll stutter; [#102](https://github.com/reqable/re-editor/issues/102): large-content performance) mean its "extremely high performance" claim would need our own measurement regardless of adoption — no different from the perf harness this milestone already runs against `EditableText` (W10).
- Any fork would concentrate changes in exactly the two files (`_code_highlight.dart`, `_code_paragraph.dart`) upstream keeps actively patching, creating an ongoing rebase-conflict tax distinct from a one-time adoption decision.

**Decision: not pursued for v1.** `EditableText` plus viewport-scoped decoration (this milestone's actual design) is judged sufficient for realistic note/log file sizes. **Revisit trigger:** real, recurring user reports of large-file editing performance problems post-launch that the measured size threshold and viewport-scoped decoration don't adequately resolve — at which point, re-run the single open question above (does `re_editor`'s layout path already re-invoke per-line builds on selection change) as the first step of a proper spike, rather than re-deriving this evaluation from scratch.

## Post-1.0 large-file mode fallback (depends on `FR-11`, backlog)

`milestones.md`'s Post-1.0 backlog adds four selectable Markdown view/edit modes: **Live Preview** (this milestone's default), **View-only** (rendered, read-only), **Raw edit** (plaintext, no decoration), and **Side-by-side** (raw edit left / view-only right, vertical split). Once that ships, the plan is:

- Live Preview is **disabled above a configured line-count threshold** (documented default: **1,000 lines**, but see the caveat below — this is a placeholder, not a number derived from measurement). Opening an over-threshold file while in Live Preview mode instead opens it in **Raw edit mode**, with a **dismissable banner** at the top of the editor pane explaining that Live Preview is disabled for files over the threshold.
- The mode switcher still offers **View-only** and **Side-by-side** for that file; only the **Live Preview** option is greyed out/unselectable while the file remains over threshold.
- This is a UX-level extension of exit criterion 4's existing "degrade visibly and deliberately" behavior, not a separate mechanism — same threshold concept, now surfaced through a real mode switcher instead of a bespoke undecorated-source view.

**Important caveat, worth being explicit about rather than silently assuming this fully solves large-file performance:** if Raw edit mode is implemented as `EditableText` with decoration turned off, it removes the *extra* relayout Live Preview causes (glyph widths changing as markup reveals/collapses on cursor movement) but does **not** remove the underlying `EditableText` ceiling itself — [flutter/flutter#114158](https://github.com/flutter/flutter/issues/114158) reproduces its lag on a **plain** `TextField` with no custom decoration at all. So Raw edit mode on a very large file should be *less* laggy than Live Preview on the same file, not necessarily *fast*. **View-only mode is the one mode that can plausibly be fast at any size**, because being read-only it doesn't need `EditableText` at all — a virtualized, read-only rendering (`ListView.builder`/`Sliver`-based, rendering only visible blocks) is a legitimate, structurally different path that actually scales, unlike anything editable in this document's architecture. Side-by-side's right pane inherits that same benefit; its left (raw edit) pane does not.

**On the 1,000-line default specifically**: treat it as a documented starting point, not a conclusion. The actual threshold this milestone's own W0/W10 perf harness produces (benchmarked at 500/2,000/10,000 lines, per exit criterion 4) is the authoritative number once it exists — reconcile the two when this backlog item is picked up, rather than shipping two independently-chosen thresholds.

## Explicitly out of M6

Table grid rendering; image/attachment embedding (N-06, COULD); real `![[embed]]` transclusion; folding/outlining; the graph and canvas views (PL-06/PL-07, post-1.0); collaborative or multi-caret editing (X-02); AI-assisted or auto-formatting behaviour (X-05 — the editor never rewrites bytes the user didn't ask it to rewrite); vim/emacs keymaps; the quick switcher itself (N-04, M9) as distinct from the autocomplete overlay it shares; the View-only/Raw-edit/Side-by-side modes themselves (`FR-11`, post-1.0 backlog) — this milestone ships Live Preview only, with its size-threshold degradation as a bespoke fallback until `FR-11` exists to generalize it into real mode switching.

## Notable properties this design gets for free

Worth recording, because they are the payoff for §7's constraint and should be regression-tested as features:

- **Copy/paste yields raw Markdown**, always, because the buffer *is* the file. Block editors have to serialize on copy and guess on paste.
- **A file Citrinium cannot fully parse is still fully editable** — unknown syntax renders as plain text rather than being dropped or normalized, which is what makes P-11's portability claim honest under editing, not just under reading.
- **Undo is Flutter's**, operating on text, so it can never desynchronize from a document model.
